The filter subsystem is intentionally decoupled from result presentation. The same filter controls should work for grid, list, and any future view mode without re-authoring filter logic.

## Composition stack

- `filter-toolbar`: shell for count, actions, and mobile/desktop behavior
- `filter-button`: per-filter trigger and chip state
- `range-filter` / other control primitives: value capture
- result view: consumes canonical filter state; never owns filter UI rules

## Rules

- Keep filter state in one canonical model per page.
- Filter UI reads/writes that model; result layouts subscribe to it.
- Preserve applied state across grid/list switches.
- Show active filter count and clear-all affordance consistently.
- Mobile and desktop can differ in layout, not semantics.

## URL and state guidance

- Use URL query params for shareable filters where possible.
- Keep query keys stable across view modes.
- Apply values explicitly (on Apply) for expensive filters; avoid accidental live updates on every keystroke in heavy flows.
