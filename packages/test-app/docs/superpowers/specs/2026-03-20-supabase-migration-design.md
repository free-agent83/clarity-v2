# Supabase + Drizzle Migration Design

Migrate the mock data layer (`/data`) to a self-hosted Supabase Postgres instance with Drizzle ORM, while keeping the API layer contracts unchanged so pages require zero modifications.

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Supabase services | Postgres + Auth + Storage | Auth for jeweller login; Storage for product images (future) |
| ORM | Drizzle | Strong TypeScript inference, SQL-like syntax, pairs with Supabase client for Auth/Storage |
| DB queries | Drizzle | All queries go through Drizzle; Supabase JS client is only for Auth + Storage |
| API layer | Signatures unchanged | Pages stay untouched; only internals of `lib/api/*.ts` get rewired |
| Container management | Supabase CLI (project-level devDependency) | Manages Docker Compose stack; no global dependencies |
| Migration approach | Schema-first, then rewire | Define all tables upfront, seed all data, then rewire API files one by one |
| Type source of truth | Drizzle `$inferSelect` / `$inferInsert` | Replaces `types/` directory; resolved types in API files stay hand-written |
| Enums | `pgEnum` | ProductType, OrderStatus, OrderProgressStep, ImageType enforced at DB level |
| Seed data | Current mock data | TypeScript seed script first, then generate static `seed.sql` |

Schema files are grouped by domain rather than one file per table.

## Seed Data Strategy

### Stage 1: TypeScript Seed Script (`db/seed.ts`)

Reads from existing `/data` files, inserts via Drizzle. Insertion order respects FK constraints:

1. Lookups (no dependencies)
2. Users + suppliers + addresses
3. Products + extension tables (diamonds, gemstones, melee_lots, jewelry)
4. Jewelry configuration (ring_configurations, available_metals, available_shapes)
5. Media (product_images, certifications)
6. Orders + child tables (line_items, progress, updates, item_details, summaries)
7. Invoices
8. Commerce (carts, cart_items, shortlists)

### Stage 2: Static SQL Seed

Once the TypeScript seed is verified, generate `supabase/seed.sql` from the seeded DB. This file is committed and used by `supabase db reset`. At this point `/data` and `db/seed.ts` can be removed.

## API Layer Migration

Function signatures and return types stay identical. Internals change from in-memory Map lookups to Drizzle queries.

### Pattern

Before (in-memory):
```ts
import { ORDERS } from "@/data/orders"
const lineItemByOrderId = new Map(ORDER_LINE_ITEMS.map(li => [li.order_id, li]))
const resolvedOrders = ORDERS.map(order => { /* manual joins */ })
export async function fetchOrderList(options) {
  await simulateLatency()
  return paginate(resolvedOrders, options)
}
```

After (Drizzle):
```ts
import { db } from "@/db/client"
export async function fetchOrderList(options) {
  const result = await db.query.orders.findMany({
    with: {
      lineItems: true,
      progress: { orderBy: (p, { asc }) => [asc(p.sortOrder)] },
      updates: true,
      itemDetails: true,
      summary: true,
      invoice: true,
      deliveryAddress: true,
    },
  })
  const resolved = result.map(order => ({ /* same shape transformation */ }))
  return paginate(resolved, options)
}
```

### Changes Per File

| File | Change |
|------|--------|
| `orders.ts` | 7 in-memory Maps replaced by `db.query.orders.findMany({ with: { ... } })` |
| `diamonds.ts` | Filter products by type + nested `with:` for diamond, lookups, images, cert |
| `lab-grown-diamonds.ts` | Same pattern, different product_type filter |
| `gemstones.ts` | Same pattern with gemstone-specific lookups |
| `jewelry.ts` | Nested `with:` for mount, ring configs, metals, shapes |
| `natural-melee.ts` | Simpler version of products pattern |
| `lab-grown-melee.ts` | Same as natural melee |
| `helpers.ts` | `paginate` stays as-is initially (see note below). `simulateLatency` removed. `resolveLookup` removed (Drizzle JOINs handle it) |
| `users.ts` | `db.query.users.findFirst()` |
| `addresses.ts` | `db.query.addresses.findFirst()` |
| `cart.ts` | Queries + mutations via `db.insert`/`db.update` |
| `shortlists.ts` | Queries + mutations via `db.insert`/`db.update` |

### Pagination Note

The `paginate` helper currently receives the full result array and slices in JavaScript. For this migration, it stays as-is — Drizzle queries fetch all matching rows and `paginate` slices them. This is acceptable for the current data scale (~90 products, 10 orders). Pushing pagination to the database with SQL `LIMIT`/`OFFSET` is a follow-up optimisation for when data volume grows.

### Numeric Column Note

Drizzle's `numeric()` maps to Postgres `NUMERIC`, which the postgres.js driver returns as `string` (to avoid floating-point precision loss). The current mock data uses JavaScript `number` types. Each API file's resolver function will need `Number()` or `parseFloat()` calls when mapping `numeric` columns (prices, carat, dimensions, percentages) to the existing resolved types. This is a mechanical change per file — the resolved type interfaces keep `number` fields.

## Type System Migration

### Replaced by Drizzle Inference

All raw table types in `types/` are replaced by `$inferSelect` / `$inferInsert` from the schema. The `types/` directory is removed after migration.

### Kept as Hand-Written

Resolved/denormalized types (e.g., `DiamondItem`, the flat `Order` interface in `lib/api/orders.ts`) stay as hand-written interfaces in their respective API files. These represent JOIN'd output, not table rows.

### Export Hub

`db/schema/index.ts` replaces `types/index.ts` as the single import point for all table types.

## Auth & Storage (Future-Facing)

Not fully implemented in this migration. Infrastructure is set up:

- **Auth:** `auth_user_id` column added to `users` table (nullable). No RLS policies, no auth middleware, no login flows.
- **Storage:** `product-images` bucket created in `supabase/config.toml` (public, empty). Product image URLs in seed data stay as existing S3 URLs.

### Daily Commands

| Task | Command |
|------|---------|
| Start containers | `npm run db:start` |
| Stop containers | `npm run db:stop` |
| Nuke and rebuild DB | `npm run db:reset` |
| Change a table | Edit `db/schema/*.ts` then `npm run db:generate` |
| Apply migrations | `npm run db:migrate` |
| Browse DB | `npm run db:studio` or `http://127.0.0.1:54323` |
| Run the app | `npm run dev` |

### Existing Scripts (Unchanged)

`npm run dev`, `npm run build`, `npm run lint`, `npm run typecheck` all work as before. `DATABASE_URL` must be set in the build environment for `npm run build`.

## Indexes

Primary keys and unique constraints provide the initial indexes. Additional indexes will be added based on observed query patterns once the API layer is rewired. Likely candidates:

- `products(product_type, is_active)` — filtering products by category
- `orders(user_id)` — fetching orders for a user
- `product_images(product_id)` — fetching images for a product
- `certifications(product_id)` — fetching cert for a product

These will be added as part of the API rewire step when the actual query patterns are confirmed.

## Rollback Strategy

Git is the rollback mechanism. The `/data` and `/types` directories are only deleted in a **separate, final commit** after the full migration is verified end-to-end. If anything fails before that point, reverting to the mock data layer is a `git revert` away. During migration, both layers coexist in the repo.

## Files Removed After Migration

- `/data/` (entire directory)
- `/types/` (entire directory)
- `db/seed.ts` (replaced by `supabase/seed.sql`)
